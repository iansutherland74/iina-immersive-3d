# Browser Capture → depth → side-by-side → glasses

This is the path from a chosen window to a picture on the glasses, and the defects that path had. The glasses output is one session: the source is the player or the capture, not both.

The headless check is `other/browser-capture-selftest.sh`. It does not open a window. The manual checklist at the end is the real-Mac pass.

## Flow

1. **Choose a source.** Video → Choose Capture Window lists displays, then layer-0 windows that have a title. `SCShareableContent.getExcludingDesktopWindows(true, onScreenWindowsOnly: false)` keeps full-screen windows that live on another Space. IINA's own capture window, chooser, and the player window while it is on the glasses are left out.

2. **Open the stream.** `SCStream` is configured at the window's pixel size (clamped to 3840×2160, even), `32BGRA`, queue depth 3, cursor off, 30 fps on macOS 13+. A window uses `SCContentFilter(desktopIndependentWindow:)`. A display uses `SCContentFilter(display:excludingWindows:)`. ScreenCaptureKit audio stays off. Samples are copied before the callback returns. The sample queue only keeps the newest copy and never waits on the GPU, on the main thread, or on a window re-match. The stereo pass is committed on its own queue (not the queue that presents) and the present runs from that completion. A frame older than 80 ms is dropped when a newer copy is already waiting. The depth sample is committed on that same queue and read after the stereo buffer finishes, so it does not call `waitUntilCompleted`.

3. **Frames.** The screen callback runs on the capture queue, not the main thread. Status comes from the sample-attachment CFDictionary without bridging that array to Swift. `.blank` shows the protected-video message and redraws. `.idle` or a missing image redraws. Any other status with an image is copied into a pixel buffer this process owns (`CVPixelBufferCreate` + `memcpy`), then handed to the renderer. A 30 fps timer redraws if ScreenCaptureKit goes quiet.

4. **Texture lifetime.** The copy is the only buffer the renderer locks. `CVMetalTextureCacheCreateTextureFromImage` is +1 and `CVMetalTextureGetTexture` is not. The holder is released before the cache is flushed, and the flush is every 30th frame, not every frame. Flushing while the holder is alive frees the texture the holder releases next. The ScreenCaptureKit buffer is not released again. The first frame logs mean luma (`first frame luma`). `capture latency` is the milliseconds from that copy to the present, logged about once a second.

5. **Depth and side-by-side.** Capture and the player each have a compositor, because the player pass runs on the OpenGL thread. Both call `Immersive3DController.submitFrame` → `immersiveStereo`. Capture forces the pass on (`colorIsBottomUp == false` means "this texture is the picture"). Until a depth map exists, a flat 0.5 depth texture is used, so the first frames are still side-by-side. A capture texture is sampled in full by each eye (`colorIsPicture`). A player texture is the glasses framebuffer, so a 16:9 picture on 3840×1080 is the center band and each eye samples that band.

6. **One glasses output.** `GlassesSession` is the state. `Play on Glasses` (menu item, the submenu display, the panel Exit button, and Send Capture to Glasses) calls the same transition.
   - Capture running, glasses off → pin the capture window borderless on the glasses. The player window stays put.
   - Capture not running → pin the player, as before.
   - Already on the glasses → leave.
   - Capture starts while a glasses display is connected → the capture takes the output. If the player was there, it is returned and restored when capture stops.
   - Capture stops → the capture window returns to the 960×540 preview, unless the player was displaced and should come back.
   - A screen-parameter change updates the recorded display and the existing pin runs again (2D/3D size change included).

7. **Drawable size.** `GlassesDrawable.pixels` is `points × backingScaleFactor`, rounded, and refuses anything under 32 pixels on a side. Glasses use the glasses screen's full pixel size, stored when the capture is pinned. A resize or screen change while the window is moving does not read `window.screen`: a Space animation reports the Mac's built-in display (3024×1964 at 2x) or a partial frame (3840×1027), and those are ignored. After the first `nextDrawable`, the size is written on the next main-queue turn, never in the turn that took the drawable and never from `endPresent` in that same turn. Quit's `setFrame` uses `display: false` so the Apple Event pool does not take another drawable and then resize it. If the texture and the drawable differ, the frame is scaled onto the drawable instead of skipped. Present does not wait for the GPU, and the in-flight slot is released in the command-buffer completion, including on error.

8. **Window follow.** Every 0.5 s. The current window id stays selected while it is in the list, including when `isOnScreen` is false because full screen moved it to another Space. Untitled and tiny windows are placeholders and are never chosen. The filter changes only after the current id has been missing for more than 1.5 seconds, and it does not change again on the next tick. The replacement prefers a title that contains the previous title, then the largest real window of that app. If none is left, the display the window was on is captured. The shareable content and the filter are kept alive until `updateContentFilter` returns, and the filter is not updated when the id did not change.

9. **Audio.** Default is off. While a capture is running the same toggle stays on a panel on the built-in display, with a status line that says whether **IINA Capture Audio** was found, and the log says why routing did or did not start (`routing not started: the toggle is off. Sound stays in the other app.` when it was left off). A normal file is left alone: the toggle does nothing until a capture is running, and it never changes mpv's device on its own. Muting Chrome also mutes what ScreenCaptureKit can read, so there is no mute control and `capturesAudio` stays off. **Route browser sound through IINA (no echo, synced)** installs the bundled HAL plugin `IINA Capture Audio` (stereo, 48 kHz) into `/Library/Audio/Plug-Ins/HAL` with one admin prompt, then restarts `coreaudiod`. While a capture is running, IINA writes the current default output to Application Support, pins every mpv instance to `coreaudio/<that uid>`, and only then sets both `kAudioHardwarePropertyDefaultOutputDevice` and `kAudioHardwarePropertyDefaultSystemOutputDevice` to `IINACaptureAudio_UID`. Each set is read back. The log line includes the UID, the device id, the property, and the OSStatus (number and fourcc). "Restored" is logged only when that read-back matches. The browser plays into the plugin. `coreaudiod` calls ReadInput before WriteMix, so a read at the write head used to be silence for the whole capture. That read now returns the last completed buffer, and so does a read whose sample time does not overlap the write (macOS 13.7 can put input and output on different parts of the timeline). A silent WriteMix from IINA's own IO proc is ignored. A WriteMix that still contains audio is kept even when it is tagged with the reader's client id. The device clock jumps by every elapsed period; advancing one period per call left IO stalled. Playback is an IO proc on the UID in `capture-output-restore.txt`, at that device's rate and channel count (44.1 kHz or 48 kHz, 2 ch). Pinning the capture on the glasses does not stop the reader; the output is opened again after the display settles. A volume scalar of 0, or a mute, on IINA Capture Audio is raised back to full at reader start and the OSStatus is logged. The orange microphone indicator means the input IO proc is running. macOS still fills those buffers with zeros until Microphone access is authorized; `NSAudioCaptureUsageDescription` does not cover that prompt. `NSMicrophoneUsageDescription` is set, and the reader calls `AVCaptureDevice.requestAccess(for: .audio)` before `AudioDeviceStart`. The log line is `loopback mic authorization` with the status and `input=live` or `input=silence`. `loopback in rms=0.0000 samples=silence` means buffers arrived and were zeros; `samples=none` means no buffer arrived. The first non-zero buffer logs `loopback in signal`. Playback starts at delay 0 and does not wait for the first presented frame; a later `capture latency` measurement, plus the saved **Audio sync** offset (-500 to +2000 ms), tightens the delay. Positive offset holds the picture, and the video queue keeps 2000 ms of frames at the 30 fps capture rate, dropping the oldest once that frame count is full. A sample far above the recent latency is not copied into the delay. Samples more than about 200 ms late are dropped. Once a second the log has `loopback in rms=` and `loopback out rms=`. The same lines, the default-output set and restore lines (UID, device id, OSStatus), and the errors are appended to `~/Library/Logs/IINA/capture-audio.log`, which rotates at about 200 KB, because unified logging redacts them. The reader and the output each log the device when they start, and `loopback delay N ms offset N ms` is logged when playback starts and when the delay changes. The slider is in the capture controls, the glasses panel, and Settings → Audio, and the label updates as it moves. Stop, quit, and the next launch after a crash put that saved output back. **Uninstall IINA Capture Audio…** removes only that plugin. The driver is built and ad-hoc signed in CI and copied into `IINA.app` before the zip; CI does not install it or restart `coreaudiod`. Its `AudioServerPlugIn` vtable is the one `coreaudiod` on macOS 13.7 uses (184-byte interface, IO-cycle info 224 bytes, `mOutputTime` at offset 144). The plugin minimum OS is 12.0. CI runs `otool -l` on every Mach-O in the app, including this plugin and `libiina_whisper.dylib`, and fails the build if any `LC_BUILD_VERSION` minos is newer than 13.0. A headless tone is pushed through the same loopback and must come back non-silent. That test does not run inside `coreaudiod`.

10. **Teardown.** Stop cancels the follow and redraw timers, stops audio and the tap, and `stopCapture` with `ignoreStop` set so that stop is not treated as a crash. Three failed restarts give up and tell the session the capture stopped. Quit handles the route restore and `stopAll` inside `applicationShouldTerminate`, on the Apple Event's autorelease pool. The capture window is ordered out and returned with `display: false`. Any drawable resize is postponed to the next main-queue turn. `exitGlasses` does the same for the player window. The self-test's quit-during-capture case refuses a resize while that pool still holds a drawable, under AddressSanitizer and under `NSZombieEnabled`.

## Defects

| High | Play on Glasses was not a capture source | The menu moved the player window. Capture had a second flag and a second window. Pressing Play on Glasses never sized or presented the capture drawable, which is why the log had no `output drawable` or `glasses send`. |
| High | Capture did not take connected glasses | Starting a capture left the picture on the preview even when a glasses display was already there. |
| High | Full-screen YouTube dropped the track | The id and the title both change. Follow required the title to match, then logged `tracked window N is gone; no app+title match` and kept the dead filter. |
| High | Full-width side-by-side cropped the capture | `contentRect` assumes the color texture is a 3840×1080 framebuffer with the picture pillarboxed. A capture texture is the window. Each eye sampled the center band of that window. |
| Medium | Two booleans for one output | `glassesActive` and `onGlasses` could disagree, and both windows could be pinned. Screen changes updated them separately. |
| Medium | Drawable size had no single formula | A zero view used to become 2×2 (`880cd67` stopped that clamp). Play on Glasses still never asked for a glasses-sized drawable. Sizes under 32 pixels are now refused. |
| Medium | Stream give-up left the session on capture | Three restart failures tore the stream down and did not tell the glasses session. |
| Medium | In-flight slot could stick | Fixed in `880cd67`: the slot is released in the command-buffer completion, including errors, and a slot busy for more than a second is reclaimed. A late completion is ignored if the slot was reused. |
| Low | Present-skip logs could flood | Skips are logged at most once a second. |
| Low | First-frame luma was a private string | The number is logged with `privacy: .public`. |

A failed translate falls back to the device list. |
| Medium | Capture latency spiked to 181 / 213 / 575 ms | Crop, the depth readback, and the stereo pass each called `waitUntilCompleted` on the queue that also presents, so one glasses blit held the next frame. | Low | No way to nudge loopback sync | **Audio sync** is a -500 to +2000 ms slider in the capture controls, the glasses panel, and Settings. Positive delays the picture. Negative delays the sound. It is saved and added to the measured delay. |

ScreenCaptureKit audio stays off. | High | Route on, and the capture was silent | Chrome and IINA both had IO on `IINACaptureAudio_UID`, and the playback device moved to the speakers, but ReadInput was asked for the sample time at the end of the last write. A read at the write head now returns the last completed buffer. The reader's own silent WriteMix is ignored. Playback starts at delay 0. The log lines are `loopback reader started`, `loopback in rms=`, `loopback output started`, `loopback out rms=`, and `loopback delay`. |
| High | Route on, the glasses UID was saved, and nothing was audible | The default output became `IINACaptureAudio_UID` and `capture-output-restore.txt` held the SmartGlasses DisplayPort UID, but the output engine stayed at 48 kHz and did not open that device. A read that missed the last write was zeros, the HAL clock advanced one period per call, and a mix tagged with the reader client was dropped. A volume of 0 on IINA Capture Audio muted the read. The output IO proc now opens the restore-file UID at the device rate (44.1 kHz or 48 kHz, 2 ch). A missed read returns the last buffer. The clock catches up. A non-silent mix is kept. | High | Every frame logged `glasses send failed`, and the route toggle was gone | `submitFrame` returns false only from the synchronous guards (stopped, no device, pipeline, depth, immersive 3D off, or no command buffer). The chooser closes when capture starts and the toggle defaults off, so the loopback never started and there was no `loopback reader started` line. ## Residual risks

- CI has no glasses and no Screen Recording prompt. The self-test checks the session, the pixel lock, the window follow (including the untitled-window flip), frame dropping, the quit-during-capture resize rule, the latency spike filter, the sync offset, the default-output read-back rule, the audio policy, the route order (player first, then the system output, then restore, including a crash file), the loopback ring, a tone through that loopback (a read at the write head, and a read on a different sample-time timeline, must not be silence; a non-silent mix tagged as the reader is kept; the clock catches up every elapsed period), the playback device taken from the restore file at 44.1 kHz and 48 kHz, the microphone authorization log (`input=live` only when authorized, and a prompt before the reader starts), and the capture-audio.log rotation, the texture retain loop, a scaled 1920×1080 frame, and one synthetic frame through `immersiveStereo` at 3840×1080. It does not present to a `CAMetalLayer` or capture a real window. AddressSanitizer does not see ScreenCaptureKit.
- Flat depth is used until the depth model returns a map. The picture is side-by-side with little parallax until then. A protected window stays black on purpose.
- The HAL plugin is ad-hoc signed, the same as IINA.app. It installed on the macOS 13.7.8 test machine. A different Mac can still refuse an ad-hoc plugin. The picture capture still runs with the browser's own sound.
- Changing the system default output silences every app, not only the browser, until capture stops or IINA launches again after a crash. Alerts move with `DefaultSystemOutputDevice` and come back with it. Every mpv window is pinned to the active player's previous device for the capture and restored to that one device. If a set still fails, the log has the OSStatus and the device ids; CI cannot call `coreaudiod`.
- CI compiles the plugin against the current SDK and checks that the vtable layout is still the macOS 13.7 layout. It does not copy the plugin into `/Library/Audio/Plug-Ins/HAL` and it does not restart `coreaudiod`. The whole app is rejected if any Mach-O minimum OS is newer than 13.0.
- The follow timer skips a tick when start or stop holds the session lock.
- Three frame slots cover the stereo pass, the blit, and one frame waiting on the main thread. A newer finished frame frees the one that was waiting. A slot that is still busy, queued, or being presented is not reused, even after a second. If all three stay busy the frame is skipped (`glasses send skipped; previous frame is still on the GPU`) instead of aliasing the texture. `glasses send failed: …` names the guard when `submitFrame` returns false.
- Taking the glasses from the player and giving them back calls the mirror restore and the mirror split around that handoff.

## Manual test

On a Mac with Screen Recording allowed, and the glasses connected:

1. Start a capture of a Chrome window that is showing a normal page (not DRM). The preview should show it. The log should contain `output drawable` at the preview pixel size (960×540 points times the scale) and `glasses send` at that size, plus `first frame luma` well above 0. `glasses send failed` should not appear. If it does, the text after the colon is the guard that returned. `released stuck frame slot` should not appear.
2. Press **Play on Glasses** (Video menu). The capture window, not the player, should go borderless on the glasses at the screen pixel size (3840×1080 or 1920×1080). The log should contain `glasses source capture` and `output drawable` at that size. Both eyes should show the whole window, not a center crop and not black.
3. Press **Play on Glasses** again. The capture should return to the preview. The player window should not have moved.
4. Quit the capture. Start it again with the glasses still connected. The capture should land on the glasses without another click.
5. Put YouTube full screen in Chrome. The log must not flip every half second between the YouTube window and an untitled window. The picture should stay on the YouTube window. `output drawable` should stay at the glasses size (3840×1080 or 1920×1080) through the animation, not 3024×1964 or 3840×1027. A line `glasses present scale failed` or `present skipped texture` means the rescale path failed. `capture latency` should stay near a few tens of milliseconds while the picture moves. A single `dropped a late capture frame` line is a stall that was not shown. Leave full screen and confirm the same window is still followed.
6. With **Route browser sound through IINA (no echo, synced)** off, sound comes from Chrome once. IINA does not play a delayed copy. There is no Mute control. A **Browser Capture** panel on the built-in display shows that toggle for the whole capture, and a status line that says whether **IINA Capture Audio** was found and that sound stays in the other app. The log contains `IINA Capture Audio: found (IINACaptureAudio_UID).` or `IINA Capture Audio: not found. Turning the toggle on asks to install it.` and `routing not started: the toggle is off. Sound stays in the other app.` Play a normal file with the toggle off, and again with the toggle on but capture stopped. The output device does not change either time.
7. Turn the toggle on. macOS asks once for an administrator password and installs **IINA Capture Audio**. Start a capture of a page that is playing sound. The log, and `~/Library/Logs/IINA/capture-audio.log`, should contain `default output is IINACaptureAudio_UID` with a device id and `status=0`, not `could not change the default output`. The first capture asks for Microphone access. The log should contain `loopback mic authorization authorized` with `usageDescription=present` and `input=live` before `loopback reader started`. `input=silence`, or `denied`, means System Settings → Privacy & Security → Microphone is off for IINA and the reader will stay at zero until that is turned on and the capture is started again. It should also contain `loopback reader started device=` with `uid=IINACaptureAudio_UID format=48000 Hz 2ch float32`, then `loopback in signal` once the first non-zero buffer arrives, and about once a second `loopback in rms=` with a value above `0.0000` while the page is audible. `loopback in rms=0.0000 samples=silence` means buffers arrived and were zeros; `samples=none` means no buffer arrived, `loopback output started device=` with the real speaker uid (the glasses UID from `capture-output-restore.txt`) and `rate=` of `48000` or `44100`, `loopback delay 0 ms offset`, and about once a second `loopback out rms=` above `0.0000`. `loopback device volume=` should not stay at `0.0000`. Chrome goes quiet, including alert sounds, and IINA plays that sound on the previous output (glasses or headphones). `loopback delay` changes when a picture measurement arrives. **Audio sync** (-500 to +2000 ms) is in the capture controls, the glasses panel, and Settings → Audio. The label updates while the slider moves, and the value is still there after a relaunch. Moving it later or earlier should be audible on top of the automatic delay. `glasses send skipped; previous frame is still on the GPU` may appear during a stall; it should not be continuous for the whole capture. Stop the capture. The log should say the default output was restored, and only say that when it was. Chrome is heard from itself again. `loopback in rms=0.0000` for the whole capture means the driver is still handing silence.
8. Quit IINA while a capture is on the glasses and the route is on. It must not crash. The next launch should still have the previous output, not **IINA Capture Audio**.
9. Start a capture with the toggle on, then force-quit IINA from Activity Monitor. Launch it again. The previous output is back before a video starts. **Uninstall IINA Capture Audio…** removes the plugin and asks for an administrator password.
10. With nothing capturing, **Play on Glasses** should still move the player, and Exit should restore it.
11. Start a capture while the player is already on the glasses. The player should leave and the capture should take the display. Stop the capture. The player should come back.
12. A DRM video should log a low `first frame luma` and the protected-window message. The glasses stay black. That is the intended result.
